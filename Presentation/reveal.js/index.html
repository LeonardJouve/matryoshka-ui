DSL

L'interface est un arbre d'éléments immuables

Trois types d'éléments

  • Div : Conteneur de layout (enfants)
  • Text : Chaîne de caractères
  • Image : Asset chargé via un chemin

Philosophie Flex

  • Axes Principal et Transversal
  • Sizing, Spacing, Alignment
  • Construction via Root(Div(...))

Conteneur : Div

Modificateurs Uniques

  • LayoutAxis : Horizontal / Vertical
  • Padding : Inner spacing
  • Gap : Spacing entre enfants
  • Justify & Align : Flexbox logic
  • BorderRadius : 0..1 (Corner radius)
  • BorderWidth/Color : Bordures

Feuille : Text

Modificateurs Text

Feuille : Image

Modificateurs Image

  • Width & Height : Sizing de l'asset

Usage

Image("assets/logo.png",

    Width(Fixed(100)),
    Height(Fixed(100)),
  ),
)

Sizing : LayoutSize

Bottom-Up (Sizing)

  • Fit() : Taille du contenu (défaut)
  • Fixed(size) : Taille absolue en pixels

Top-Down (Flex)

  • Grow(factor) : Remplit l'espace restant
  • Percent(%) : % de la taille du parent

Attention sur Percent

Percent est résolu après le parent. Il s'effondre à 0 dans un parent Fit(). À utiliser uniquement dans des parents Fixed, Grow ou Percent résolus.

Défis Techniques

Séparation en Phases

Maintenir des phases de calcul (Sizing vs Flex) strictement isolées malgré les dépendances croisées entre parents et enfants.

Conflit de Résolution

Gérer les éléments dont la taille dépend du parent (Percent/Grow) sans briser l'algorithme récursif de remontée des tailles (Fit).

Limitation : Div Wrapping

Le problème du Wrapping

L'implémentation du wrapping des enfants dans les conteneurs (similaire au flex-wrap) pose des défis majeurs :

  • Multi-Lignes : La hauteur totale du parent devient dépendante de la largeur résolue et du nombre de lignes créées.
  • Phases Croisées : Le calcul de la position impacte le calcul de la taille, brisant la séparation stricte des phases.

Verdict : Garantir un rendu sans bug avec du wrapping demandait une complexité algorithmique (gestion des overflows, alignement par ligne) impossible à stabiliser dans le temps imparti.

Architecture Renderer

Indépendance totale vis-à-vis de l'affichage

Le Concept : Renderer Agnostic

Le moteur de layout produit des coordonnées (x, y, w, h). N'importe quelle technologie peut ensuite les dessiner.


type Renderer interface {
	InitWindow(width, height int, title string)
	Render(element *dsl.Node)
	CloseWindow()
}

Retour d'expérience : Paradigme

Paradigme Déclaratif

  • Abstraction du résultat : Interface intuitive décrivant le "quoi" plutôt que le "comment".
  • Équilibre API/DSL : Point clé entre la fidélité au domaine métier et la faisabilité technique de la résolution.
  • Design restrictif : Importance de concevoir une interface empêchant les états impossibles ou incohérents.
  • Anticipation architecturale : Blocages rencontrés lors de l'ajout du texte et des images par manque de vision globale initiale.

Retour d'expérience : Go

Le Langage Go

  • Apprentissage : Choix délibéré pour approfondir nos connaissances malgré le manque de maîtrise initiale.
  • Simplicité paradoxale : Le minimalisme (25 mots-clés) facilite l'immersion mais exige une rigueur accrue dans la structure.
  • Composition vs Héritage : Nécessité de repenser les Design Patterns classiques (ex: styles communs) au profit de la composition.
  • Liberté d'implémentation : Absence de restrictions imposées par le langage sur la création de notre propre paradigme.

Conclusion

  • Complexité sous-estimée : Ambitions peut-être trop optimistes face aux défis d'un moteur de mise en page.
  • Courbe d'apprentissage : Le choix d'un nouveau langage (Go) a complexifié le développement initial.
  • Défis Techniques : Difficultés majeures avec la gestion des overflows et le débogage algorithmique.
  • Bilan Positif : Expérience riche en architecture, choix d'implémentation et conception d'interfaces déclaratives.
